# แผนทางเทคนิค: จัดการบัญชีผู้ใช้

ไฟล์ข้อกำหนดอ้างอิง: `spec.md`

Spec ID: `SPEC-ACC-001` | สถานะข้อกำหนด: `Draft v1`

## 1. สรุปแนวทาง

1. สร้างหน้าจัดการบัญชีสำหรับ Resident ที่เข้าสู่ระบบแล้ว
   (`CON-ACC-01`, `FR-ACC-01`)

2. แสดงข้อมูลบัญชีปัจจุบันและรองรับการแก้ไขข้อมูลส่วนตัว
   (`FR-ACC-02`)

3. ตรวจสอบข้อมูลก่อนบันทึก และแสดงข้อความเมื่อข้อมูลไม่ถูกต้อง
   (`FR-ACC-03`, `AC-ACC-03`)

4. สร้างส่วนเปลี่ยนรหัสผ่าน โดยต้องตรวจสอบรหัสผ่านเดิมก่อน
   (`FR-ACC-04`, `FR-ACC-05`)

5. บันทึกข้อมูลบัญชีและแสดงข้อมูลล่าสุดหลังบันทึกสำเร็จ
   (`FR-ACC-06`, `FR-ACC-07`)

6. รองรับการยกเลิกการแก้ไขโดยไม่บันทึกข้อมูล
   (`FR-ACC-08`)

7. เพิ่มการทดสอบตาม Acceptance Criteria และตรวจสอบข้อกำหนดด้านความปลอดภัย
   (`NFR-SEC-01`, `NFR-SEC-02`)

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| Web UI ตาม stack ของโครงการ | ทีมเลือกเอง | ใช้สร้างหน้าจัดการบัญชี |
| API ตาม stack ของโครงการ | ทีมเลือกเอง | ใช้โหลดและอัปเดตข้อมูลบัญชี |
| ฐานข้อมูลของโครงการ | ทีมเลือกเอง | ใช้เก็บข้อมูลบัญชี |
| Password hashing | `NFR-SEC-01` | ใช้สำหรับจัดเก็บรหัสผ่านอย่างปลอดภัย |
| Automated testing ของ stack | ทีมเลือกเอง | ใช้ตรวจสอบ Acceptance Criteria |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับ |
|---|---|---|
| `User` | `id`, `name`, `phone`, `email`, `password_hash` | `FR-ACC-01`, `FR-ACC-02`, `FR-ACC-04`, `CON-SEC-01` |
| `PasswordChangeRequest` (ข้อมูลชั่วคราว) | `current_password`, `new_password`, `user_id` | `FR-ACC-04`, `FR-ACC-05` |

กติกาข้อมูล:

- การอ่านและแก้ไขข้อมูลต้องอ้างอิงจากผู้ใช้ที่เข้าสู่ระบบ
  (`CON-ACC-01`, `CON-ACC-02`)
- ระบบต้องไม่ส่ง `password_hash` กลับไปแสดงบนหน้าเว็บ
- ก่อนเปลี่ยนรหัสผ่านต้องตรวจสอบรหัสผ่านเดิม
  (`FR-ACC-05`)
- รหัสผ่านใหม่ต้องถูกจัดเก็บในรูปแบบที่ปลอดภัย
  (`NFR-SEC-01`)

## 4. API / หน้าจอ

| รายการ | Input หลัก | Output หลัก | รองรับ |
|---|---|---|---|
| `GET /account` | session/authenticated user | ข้อมูลบัญชีที่อนุญาตให้แสดง | `FR-ACC-01` |
| `PUT /account` | ชื่อ, เบอร์โทรศัพท์, ข้อมูลที่อนุญาตให้แก้ไข | ข้อมูลบัญชีล่าสุด | `FR-ACC-02`, `FR-ACC-06`, `FR-ACC-07` |
| `PUT /account/password` | รหัสผ่านเดิม, รหัสผ่านใหม่ | สถานะการเปลี่ยนรหัสผ่าน | `FR-ACC-04`, `FR-ACC-05` |
| หน้าจัดการบัญชี | ข้อมูลส่วนตัว, ปุ่มบันทึก, ปุ่มยกเลิก | ข้อมูลล่าสุดหรือข้อความผิดพลาด | `FR-ACC-01` ถึง `FR-ACC-08` |

หมายเหตุ: ชื่อ API เป็นสัญญาเชิงตรรกะสำหรับการวางแผน
ทีมต้องใช้รูปแบบ API และ authentication ที่มีอยู่ในโครงการจริง

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| `CON-ACC-01` | ตรวจ authentication ก่อนเรียก API และเปิดหน้าจัดการบัญชี | ใช้แล้ว |
| `CON-ACC-02` | API ใช้ user/session ปัจจุบันในการอ่านและแก้ไขข้อมูล | ใช้แล้ว |
| `CON-SEC-01` | ใช้ password hashing และไม่เก็บ password แบบ plain text | ใช้แล้ว |
| `CON-UI-01` | ออกแบบหน้าจอให้รองรับ desktop และ mobile | ใช้แล้ว |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| `AC-ACC-01` | `test_AC_ACC_01_view_account` | เข้าสู่ระบบด้วย Resident แล้วเปิดหน้าจัดการบัญชี ตรวจว่าข้อมูลปัจจุบันถูกแสดง |
| `AC-ACC-02` | `test_AC_ACC_02_update_account` | แก้ไขข้อมูลส่วนตัวและกดบันทึก ตรวจว่าข้อมูลใหม่ถูกบันทึก |
| `AC-ACC-03` | `test_AC_ACC_03_reject_invalid_account_data` | ส่งข้อมูลที่ไม่ครบหรือรูปแบบไม่ถูกต้อง ตรวจข้อความแจ้งเตือนและตรวจว่าไม่บันทึก |
| `AC-ACC-04` | `test_AC_ACC_04_change_password` | ใช้รหัสผ่านเดิมที่ถูกต้องและรหัสผ่านใหม่ ตรวจว่าสามารถเปลี่ยนรหัสผ่านได้ |
| `AC-ACC-05` | `test_AC_ACC_05_reject_wrong_current_password` | ใช้รหัสผ่านเดิมผิด ตรวจว่า API ปฏิเสธและรหัสผ่านไม่เปลี่ยน |
| `AC-ACC-06` | `test_AC_ACC_06_cancel_account_update` | แก้ไขข้อมูลแล้วกดยกเลิก ตรวจว่าข้อมูลเดิมยังอยู่และไม่มีการบันทึก |
| `AC-ACC-07` | `test_AC_ACC_07_update_success_message` | บันทึกข้อมูลสำเร็จ ตรวจข้อความยืนยันและข้อมูลล่าสุดบนหน้าโปรไฟล์ |

การทดสอบเพิ่มเติม:

- ตรวจว่า Guest ที่ยังไม่ได้เข้าสู่ระบบไม่สามารถเรียก API จัดการบัญชีได้
  (`CON-ACC-01`)
- ตรวจว่า Resident ไม่สามารถแก้ไขข้อมูลของ User คนอื่น
  (`CON-ACC-02`)
- ตรวจว่า `password_hash` ไม่ถูกส่งกลับใน API response
  (`NFR-SEC-01`)
- ตรวจ responsive layout บน desktop และ mobile
  (`CON-UI-01`)
- ตรวจ response time ของการอัปเดตข้อมูลบัญชีไม่เกิน 2 วินาทีในสภาวะปกติ
  (`NFR-ACC-01`)

## 7. ลำดับงาน

1. ตรวจสอบโครงสร้าง User และ authentication ที่มีอยู่ในโครงการ
2. กำหนดข้อมูลบัญชีที่ Resident สามารถแก้ไขได้
3. สร้าง API สำหรับอ่านและอัปเดตข้อมูลบัญชี
4. เพิ่ม validation สำหรับข้อมูลส่วนตัว
5. สร้าง API สำหรับเปลี่ยนรหัสผ่านและตรวจสอบรหัสผ่านเดิม
6. สร้างหน้าจัดการบัญชีและส่วนเปลี่ยนรหัสผ่าน
7. เพิ่มปุ่มบันทึกและยกเลิก
8. เพิ่มข้อความแจ้งเตือนกรณีสำเร็จและกรณีข้อมูลไม่ถูกต้อง
9. เพิ่ม automated tests ตาม `AC-ACC-01` ถึง `AC-ACC-07`
10. ตรวจสอบ security, responsive และ performance ตาม NFR

## 8. สิ่งที่ยังไม่ทำ

ฟีเจอร์ต่อไปนี้ไม่อยู่ในแผนของ UC-08:

- การสมัครสมาชิก ซึ่งเป็นหน้าที่ของ UC-02
- การเข้าสู่ระบบ ซึ่งเป็นหน้าที่ของ UC-07
- การจัดการบัญชีของผู้ใช้คนอื่นโดย Admin
- การลบบัญชี
- การเปลี่ยนบทบาทหรือสิทธิ์ของผู้ใช้

รายละเอียดเพิ่มเติมที่ยังต้องยืนยันคือข้อมูลส่วนตัวเพิ่มเติมที่ Resident
สามารถแก้ไขได้ นอกเหนือจากชื่อและเบอร์โทรศัพท์ (`OQ-01`)
