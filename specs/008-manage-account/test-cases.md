# Test Cases: จัดการบัญชีผู้ใช้

Spec ID: `SPEC-ACCOUNT-001` | Use Case: `UC-08`

อ้างอิง: [spec.md](./spec.md) | [plan.md](./plan.md) | [tasks.md](./tasks.md)

## ขอบเขตและเงื่อนไขการทดสอบ

- ใช้บัญชี Resident และข้อมูลทดสอบที่สร้างขึ้นสำหรับการทดสอบเท่านั้น
- ทดสอบตาม Acceptance Criteria และ IDs ใน `spec.md`; ไม่กำหนด requiredness หรือกฎตรวจชื่อแทนทีม
- กรณีทดสอบที่ขึ้นกับ Q-01, Q-02 หรือ Q-03 ให้รอคำตอบก่อนดำเนินการตามที่ระบุ
- ใช้สภาพแวดล้อมที่รองรับ HTTPS และการตรวจสอบตัวตน/session จาก UC-07; ไม่ใช้ `X-Owner-Id` prototype เป็นตัวตนสำหรับกรณีทดสอบ

## Test Cases

### TC-ACCOUNT-01: แสดงบัญชีและตรวจรูปแบบหน้าจอ

- **Test Case ID:** `TC-ACCOUNT-01`
- **Requirement/AC ID:** `FR-ACCOUNT-01`, `NFR-USE-01`, `CON-UI-01`, `AC-ACCOUNT-01`
- **Objective:** ตรวจข้อมูลบัญชีปัจจุบัน การแบ่งส่วนข้อมูลส่วนตัวกับการเปลี่ยนรหัสผ่าน และการปรับหน้าจอตามกลุ่มอุปกรณ์
- **Preconditions:** มีบัญชี Resident พร้อมข้อมูลบัญชีทดสอบ และผู้ใช้เข้าสู่ระบบด้วย session ที่ใช้งานได้
- **Test Data:** ข้อมูลบัญชีทดสอบที่บันทึกไว้; อุปกรณ์หรือ viewport ในกลุ่มมือถือ แท็บเล็ต และคอมพิวเตอร์
- **Steps:**
  1. เปิดหน้าจัดการบัญชีด้วยบัญชี Resident ที่กำหนด
  2. ตรวจข้อมูลบัญชีที่แสดงและแยกส่วนข้อมูลส่วนตัวกับส่วนเปลี่ยนรหัสผ่าน
  3. ตรวจหน้าจอบนอุปกรณ์หรือ viewport ของแต่ละกลุ่ม
- **Expected Result:** ระบบแสดงข้อมูลบัญชีของ Resident ปัจจุบัน แบ่งส่วนข้อมูลส่วนตัวและการเปลี่ยนรหัสผ่านอย่างชัดเจน และปรับรูปแบบตามขนาดอุปกรณ์ โดยไม่กำหนดเกณฑ์เชิงอัตวิสัยเรื่อง “ใช้งานง่าย” เพิ่มเติม

### TC-ACCOUNT-02: แก้ไขและบันทึกข้อมูลส่วนตัวสำเร็จ

- **Test Case ID:** `TC-ACCOUNT-02`
- **Requirement/AC ID:** `FR-ACCOUNT-02`, `FR-ACCOUNT-04`, `FR-ACCOUNT-05`, `CON-ACCOUNT-03`, `AC-ACCOUNT-01`, `AC-ACCOUNT-05`
- **Objective:** ตรวจการบันทึกข้อมูลส่วนตัวที่ถูกต้อง การแจ้งผลสำเร็จ และการแสดงข้อมูลล่าสุด
- **Preconditions:** ผู้ใช้เข้าสู่ระบบ; มีข้อมูลบัญชีเดิม; ได้ข้อสรุป Q-01 เพื่อใช้ค่าชื่อและกฎ requiredness ตามที่ทีมกำหนด
- **Test Data:** ชื่อที่เป็นไปตามข้อสรุป Q-01; เบอร์โทรศัพท์ `0812345678`; อีเมล `resident.updated@example.test`
- **Steps:**
  1. เปิดฟอร์มข้อมูลส่วนตัวและกรอกข้อมูลทดสอบ
  2. กดบันทึกและรอผล
  3. ตรวจข้อความแจ้งเตือนและข้อมูลบนหน้าโปรไฟล์หลังบันทึก
  4. ตรวจข้อมูลที่จัดเก็บไว้ในบัญชีทดสอบ
- **Expected Result:** ระบบตรวจสอบข้อมูล บันทึกข้อมูลใหม่เมื่อผ่านการตรวจ แสดงข้อความยืนยัน และแสดงข้อมูลล่าสุดบนหน้าโปรไฟล์ โดยไม่มีขั้นตอนยืนยันอีเมลใหม่ใน UC-08
- **สถานะ:** รอ Q-01

### TC-ACCOUNT-06: เปลี่ยนรหัสผ่านสำเร็จและตรวจการจัดเก็บอย่างปลอดภัย

- **Test Case ID:** `TC-ACCOUNT-06`
- **Requirement/AC ID:** `FR-ACCOUNT-03`, `FR-ACCOUNT-06`, `FR-ACCOUNT-07`, `NFR-SEC-01`, `CON-ACCOUNT-03`, `CON-ACCOUNT-04`, `CON-SEC-01`, `CON-SEC-02`, `AC-ACCOUNT-02`
- **Objective:** ตรวจการเปลี่ยนรหัสผ่านด้วยรหัสผ่านเดิมที่ถูกต้อง การจัดเก็บแบบ salted password hash การรับส่งผ่าน HTTPS การยกเลิก session เดิม และการนำผู้ใช้ไปหน้า Login
- **Preconditions:** ผู้ใช้เข้าสู่ระบบ; รหัสผ่านเดิมของบัญชีทดสอบเป็นที่ทราบ; มี Argon2 parser/verifier และวิธีรายงานผลแบบไม่เปิดเผยรหัสผ่าน, hash หรือ Salt
- **Test Data:** รหัสผ่านเดิม `CurrentPass123`; รหัสผ่านใหม่ `Abcd1234` (8 ตัวอักษร); คำยืนยัน `Abcd1234`
- **Steps:**
  1. เปิดส่วนเปลี่ยนรหัสผ่านที่แยกจากฟอร์มข้อมูลส่วนตัว
  2. กรอกรหัสผ่านเดิม รหัสผ่านใหม่ และคำยืนยันตามข้อมูลทดสอบ
  3. ส่งคำขอผ่าน HTTPS
  4. ตรวจด้วย Argon2 parser ว่า credential ที่จัดเก็บมี Salt โดยให้ผลตรวจเป็น pass/fail เท่านั้น
  5. ใช้รหัสผ่านทดสอบเดียวกันสร้าง Argon2 hash สองครั้งใน test context แล้วเปรียบเทียบ Salt ที่ parser แยกได้ โดยไม่แสดงค่า password, hash หรือ Salt ใน log/report
  6. ใช้กลไกตรวจสอบรหัสผ่านของระบบยืนยันว่ารหัสผ่านใหม่ผ่านและรหัสผ่านเดิมไม่ผ่าน โดยไม่แสดงค่า password หรือ hash
  7. ใช้ session เดิมเปิดหน้าจัดการบัญชีอีกครั้ง และตรวจการนำผู้ใช้ไปหน้า Login
- **Expected Result:** ระบบเปลี่ยนรหัสผ่านเมื่อรหัสผ่านเดิมถูกต้อง รหัสผ่านใหม่มีความยาวอย่างน้อย 8 ตัวอักษรและคำยืนยันตรงกัน; จัดเก็บเป็น Argon2 salted password hash ที่ไม่ใช่ plain text และมี Salt; การสร้าง hash จากรหัสผ่านทดสอบเดียวกันสองครั้งใช้ Salt ต่างกัน; ส่งข้อมูลผ่าน HTTPS; session เดิมใช้ต่อไม่ได้และนำผู้ใช้ไปหน้า Login โดยผลทดสอบไม่แสดงค่ารหัสผ่าน, hash หรือ Salt

### TC-ACCOUNT-10: ยกเลิกการแก้ไขข้อมูลส่วนตัว

- **Test Case ID:** `TC-ACCOUNT-10`
- **Requirement/AC ID:** `FR-ACCOUNT-08`, `AC-ACCOUNT-06`
- **Objective:** ตรวจว่า Cancel ในฟอร์มข้อมูลส่วนตัวไม่บันทึกข้อมูลนั้น และไม่ทำให้ข้อมูลหรือกระบวนการในฟอร์มเปลี่ยนรหัสผ่านถูกบันทึกหรือยกเลิกโดยไม่ตั้งใจ
- **Preconditions:** ผู้ใช้เข้าสู่ระบบ มีข้อมูลส่วนตัวเดิม และหน้าแยกฟอร์มข้อมูลส่วนตัวกับเปลี่ยนรหัสผ่าน
- **Test Data:** ข้อมูลส่วนตัวเดิมและสถานะรหัสผ่านเดิมของบัญชีทดสอบ; ค่าข้อมูลส่วนตัวที่แก้ไขแต่ยังไม่บันทึก; ค่ารหัสผ่านที่กรอกไว้แต่ยังไม่ส่งในฟอร์มเปลี่ยนรหัสผ่าน
- **Steps:**
  1. บันทึกข้อมูลส่วนตัวและสถานะรหัสผ่านเดิมของบัญชีทดสอบไว้เพื่อเปรียบเทียบ
  2. แก้ไขข้อมูลในฟอร์มข้อมูลส่วนตัวโดยยังไม่กดบันทึก
  3. กรอกข้อมูลไว้ในฟอร์มเปลี่ยนรหัสผ่านโดยยังไม่กดยืนยัน
  4. กด Cancel เฉพาะในฟอร์มข้อมูลส่วนตัว
  5. ตรวจข้อมูลส่วนตัวบนหน้าและในที่จัดเก็บ รวมถึงฟอร์มเปลี่ยนรหัสผ่าน คำขอที่ส่ง และสถานะรหัสผ่านเดิม
- **Expected Result:** ข้อมูลส่วนตัวเดิมกลับมาและไม่มีการบันทึกข้อมูลส่วนตัวที่แก้ไข; การกด Cancel ไม่ส่งคำขอเปลี่ยนรหัสผ่าน ไม่เปลี่ยนสถานะรหัสผ่านหรือ session และไม่ล้างหรือยกเลิกข้อมูล/กระบวนการที่ยังไม่ส่งในฟอร์มเปลี่ยนรหัสผ่าน

- **Objective:** ตรวจการปฏิเสธการเข้าถึงเมื่อไม่มี session ที่ใช้งานได้
- **Preconditions:** ไม่มี session หรือ session ที่เตรียมไว้ไม่สามารถใช้งานได้
- **Test Data:** URL ของหน้าจัดการบัญชีตามระบบทดสอบ; ไม่มีข้อมูลรับรอง session
- **Steps:**
  1. เปิดหน้าจัดการบัญชีโดยไม่มี session ที่ใช้งานได้
  2. ตรวจหน้าที่ระบบแสดงและตรวจว่าไม่มีข้อมูลบัญชีส่วนตัวปรากฏ
- **Expected Result:** ระบบไม่อนุญาตให้เข้าถึงข้อมูลบัญชีและนำผู้ใช้ไปยังหน้า Login

### TC-ACCOUNT-12: ปฏิเสธการเข้าถึงหรือแก้ไขบัญชีของผู้ใช้อื่น

- **Test Case ID:** `TC-ACCOUNT-12`
- **Requirement/AC ID:** `CON-ACCOUNT-02`, `NFR-SEC-02`, `AC-ACCOUNT-07`
- **Objective:** แยกตรวจการอ่านและการแก้ไขบัญชีของ Resident คนอื่น โดยใช้ identity ที่ตรวจสอบบน server
- **Preconditions:** มี Resident A และ Resident B; ผู้ทดสอบเข้าสู่ระบบเป็น Resident A ด้วย session/token ที่ตรวจสอบได้; มีข้อมูลบัญชีเดิมของ Resident B
- **Test Data:** identity ของ Resident A; ข้อมูลบัญชีเดิมของ Resident B; คำขออ่านบัญชี B และคำขอแก้ไขบัญชี B โดยใช้ตัวตนของ A
- **Steps:**
  1. บันทึกข้อมูลบัญชีของ Resident B ก่อนทดสอบ
  2. ขณะใช้ session/token ของ Resident A ส่งคำขออ่านข้อมูลบัญชี Resident B ผ่าน interface ที่ระบบทดสอบจัดให้
  3. ตรวจว่า response ของคำขออ่านเป็น HTTP 403 และข้อมูลบัญชีของ Resident B ไม่เปลี่ยนแปลง
  4. ขณะใช้ session/token เดิมของ Resident A ส่งคำขอแก้ไขข้อมูลบัญชี Resident B ผ่าน interface ที่ระบบทดสอบจัดให้
  5. ตรวจว่า response ของคำขอแก้ไขเป็น HTTP 403 และอ่านข้อมูล Resident B ด้วย test fixture ที่ได้รับอนุญาตเพื่อยืนยันว่าข้อมูลยังไม่เปลี่ยนแปลง
- **Expected Result:** ทั้งคำขออ่านและคำขอแก้ไขบัญชี Resident B ถูกปฏิเสธด้วย HTTP 403; ข้อมูลบัญชีของ Resident B ไม่เปลี่ยนแปลงหลังแต่ละคำขอ

### TC-ACCOUNT-13: วัดเวลาการแสดงผลหลังบันทึก

- **Test Case ID:** `TC-ACCOUNT-13`
- **Requirement/AC ID:** `NFR-PERF-01`, `AC-ACCOUNT-08`
- **Objective:** ตรวจเวลาตั้งแต่กดบันทึกจนระบบแสดงผลสำเร็จหรือข้อผิดพลาด
- **Preconditions:** ทีมกำหนดเงื่อนไขสภาพแวดล้อมทดสอบปกติตาม Q-03 แล้ว; มีข้อมูลบัญชีทดสอบและผู้ใช้เข้าสู่ระบบ
- **Test Data:** ข้อมูลบัญชีที่ผ่านการตรวจสอบสำหรับกรณีสำเร็จ และข้อมูลบัญชีที่ผิดรูปแบบตาม `FR-ACCOUNT-03` สำหรับกรณีข้อผิดพลาด
- **Steps:**
  1. ใช้เงื่อนไขสภาพแวดล้อมที่ทีมกำหนดและเริ่มจับเวลาเมื่อกดบันทึกข้อมูลที่ถูกต้อง
  2. หยุดจับเวลาเมื่อระบบแสดงผลสำเร็จ
  3. ทำซ้ำโดยกดบันทึกข้อมูลที่ผิดรูปแบบ และหยุดจับเวลาเมื่อระบบแสดงข้อผิดพลาด
- **Expected Result:** แต่ละกรณีแสดงผลสำเร็จหรือข้อผิดพลาดภายใน 2 วินาที ภายใต้สภาพแวดล้อมทดสอบปกติที่ทีมกำหนด โดยไม่กำหนดเงื่อนไขเครือข่ายหรือปริมาณคำขอเพิ่มเติมเอง
- **สถานะ:** รอ Q-03
