# แผนทางเทคนิค: เข้าสู่ระบบ

ไฟล์ข้อกำหนดอ้างอิง: `spec.md`

Spec ID: `SPEC-LOGIN-001` | สถานะข้อกำหนด: `Draft v1`

## 1. สรุปแนวทาง

1. สร้างหน้าเข้าสู่ระบบสำหรับ Guest, Resident, Dormitory Owner และ Admin ตาม `FR-LOGIN-01`
2. รับชื่อผู้ใช้หรืออีเมลและรหัสผ่าน แล้วตรวจสอบข้อมูลกับบัญชีที่ลงทะเบียนไว้
3. ตรวจสอบสถานะบัญชีก่อนสร้าง session หากบัญชีถูกระงับต้องไม่สามารถเข้าสู่ระบบได้ตาม `FR-LOGIN-02`
4. กำหนดสิทธิ์ตามบทบาทของผู้ใช้ และนำทางไปยังหน้าที่เหมาะสมตาม `FR-LOGIN-03`
5. รองรับกรณีไม่มีบัญชีและลืมรหัสผ่าน โดยเชื่อมต่อไปยัง flow ที่เกี่ยวข้องตาม `ALT-LOGIN-01` และ `ALT-LOGIN-02`
6. แสดงข้อความผิดพลาดโดยไม่เปิดเผยว่าชื่อผู้ใช้หรือรหัสผ่านเป็นข้อมูลที่ผิด เพื่อไม่เปิดเผยข้อมูลที่ไม่จำเป็นตาม `EX-LOGIN-01`
7. วางแผนทดสอบ Acceptance Criteria รวมถึงเวลาในการตอบสนองและความปลอดภัยของข้อมูล

| ฐานข้อมูลเชิงสัมพันธ์ | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้เก็บข้อมูลบัญชี บทบาท และสถานะบัญชี |

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับ |
|---|---|---|
| `User` | `id`, `username`, `email`, `password_hash`, `role`, `account_status` | `FR-LOGIN-01`, `FR-LOGIN-02`, `FR-LOGIN-03` |
| `Session` | `id`, `user_id`, `created_at`, `expires_at` | `FR-LOGIN-03` |
| `LoginAttempt` | `id`, `user_id`, `attempted_at`, `result` | รองรับการตรวจสอบย้อนหลังและความปลอดภัย |

กติกาข้อมูล:

- รหัสผ่านต้องไม่ถูกเก็บเป็น plain text และต้องจัดเก็บในรูปแบบที่ปลอดภัย
- ระบบต้องตรวจสอบ `account_status` ก่อนอนุญาตให้เข้าสู่ระบบ
- ระบบต้องใช้ `role` ของบัญชีเพื่อกำหนดสิทธิ์หลังเข้าสู่ระบบ
- เมื่อเข้าสู่ระบบสำเร็จต้องสร้าง session สำหรับผู้ใช้
- หากตรวจสอบชื่อผู้ใช้/อีเมลหรือรหัสผ่านไม่สำเร็จ ต้องแสดงข้อความผิดพลาดแบบเดียวกันโดยไม่ระบุว่าข้อมูลส่วนใดผิด

## 4. API / หน้าจอ

| รายการ | Input หลัก | Output หลัก | รองรับ |
|---|---|---|---|
| `POST /login` | `username_or_email`, `password` | ผลการเข้าสู่ระบบและข้อมูลบทบาทที่จำเป็น | `FR-LOGIN-01`, `FR-LOGIN-02`, `FR-LOGIN-03` |
| หน้าล็อกอิน | ชื่อผู้ใช้/อีเมล, รหัสผ่าน | สถานะการเข้าสู่ระบบและข้อความแจ้งเตือน | `FR-LOGIN-01`, `NFR-USE-01` |
| หน้าหลักหลัง Login | session, role | หน้าที่ตรงกับสิทธิ์ของผู้ใช้ | `FR-LOGIN-03` |
| ลิงก์สมัครสมาชิก | - | นำไปยัง flow สมัครสมาชิก | `ALT-LOGIN-01` |
| ลิงก์ลืมรหัสผ่าน | - | นำไปยัง flow รีเซ็ตรหัสผ่าน | `ALT-LOGIN-02` |

หมายเหตุ: ชื่อ API และ field เป็นแนวทางสำหรับการวางแผนเท่านั้น รายละเอียดจริงต้องยืนยันก่อน implementation และไม่เพิ่ม behavior ที่อยู่นอก `spec.md`

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| `AC-LOGIN-01` | `test_AC_LOGIN_01_login_with_valid_credentials` | เตรียมบัญชีที่ใช้งานได้ กรอก username/email และ password ที่ถูกต้อง ตรวจว่าสามารถเข้าสู่ระบบได้ |
| `AC-LOGIN-02` | `test_AC_LOGIN_02_redirect_by_role` | เตรียมบัญชีแต่ละ role แล้ว Login ตรวจว่าระบบนำทางไปยังหน้าตามสิทธิ์ของ role |
| `AC-LOGIN-03` | `test_AC_LOGIN_03_invalid_credentials` | กรอกข้อมูลเข้าสู่ระบบผิด ตรวจว่าระบบแจ้งเตือนโดยไม่เปิดเผยว่าข้อมูลใดผิด |
| `AC-LOGIN-04` | `test_AC_LOGIN_04_suspended_account_blocked` | เตรียมบัญชีที่ถูกระงับแล้ว Login ตรวจว่าไม่สามารถเข้าสู่ระบบได้ |
| `AC-LOGIN-05` | `test_AC_LOGIN_05_login_response_under_two_seconds` | ส่งคำขอ Login ในสภาวะเครือข่ายปกติและตรวจเวลาตอบสนองไม่เกินค่าที่กำหนด |

การทดสอบเพิ่มเติม:

- ตรวจว่ารหัสผ่านไม่ถูกส่งหรือจัดเก็บในรูปแบบที่ไม่ปลอดภัย
- ตรวจการใช้งานผ่าน HTTPS/TLS
- ตรวจ responsive layout ของหน้า Login บนคอมพิวเตอร์และอุปกรณ์พกพา
- ตรวจว่าผู้ใช้ที่ไม่มี session ไม่สามารถเข้าหน้าซึ่งต้อง Login ได้
- ตรวจว่าบัญชีที่ถูกระงับไม่สามารถสร้าง session ได้

## 7. ลำดับงาน

1. กำหนดโครงสร้างข้อมูล `User` และ `Session` ตามข้อกำหนดของ `spec.md`
2. สร้าง API สำหรับตรวจสอบข้อมูล Login
3. เพิ่มการตรวจสอบสถานะบัญชีและ role
4. เพิ่มระบบสร้าง session หลัง Login สำเร็จ
5. สร้างหน้า Login และแบบฟอร์ม username/email กับ password
6. เพิ่มข้อความแจ้งเตือนสำหรับข้อมูลไม่ถูกต้องและบัญชีถูกระงับ
7. เพิ่มการนำทางตาม role
8. เชื่อมลิงก์สมัครสมาชิกและลืมรหัสผ่านตาม flow ที่กำหนด
9. เพิ่ม automated tests ตาม `AC-LOGIN-01` ถึง `AC-LOGIN-05`
10. ตรวจสอบ HTTPS ความปลอดภัย และ responsive layout

## 8. สิ่งที่ยังไม่ทำ

ฟังก์ชันสมัครสมาชิก การรีเซ็ตรหัสผ่าน และการจัดการบัญชีผู้ใช้จะไม่สร้างซ้ำภายใน UC-07 เนื่องจากเป็น flow ที่แยกออกจากการเข้าสู่ระบบ

การจัดการสิทธิ์เชิงลึกของแต่ละฟังก์ชันจะไม่ดำเนินการในแผนนี้ โดย UC-07 มีหน้าที่ตรวจสอบตัวตนและกำหนด role เพื่อส่งต่อไปยังฟังก์ชันที่เกี่ยวข้องเท่านั้น
