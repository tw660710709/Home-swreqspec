# แผนทางเทคนิค: จัดการข้อมูลหอพัก

ไฟล์ข้อกำหนดอ้างอิง: [spec.md](./spec.md)
Spec ID: `SPEC-DOR-003` | สถานะข้อกำหนด: `Draft v2`

## 1. สรุปแนวทาง

1. ให้เจ้าของหอพักที่เข้าสู่ระบบดูรายการหอพักของตน และเพิ่มหรือแก้ไขข้อมูลตามสิทธิ์ (`CON-ACC-01`, `CON-AUTH-01`, `FR-DOR-09` ถึง `FR-DOR-12`)
2. แยกหน้าจัดการข้อมูลห้องพักออกจากหน้าจัดการข้อมูลหอพัก โดยเชื่อมข้อมูลห้องพักกับหอพักและบันทึกราคาต่อห้องเป็นบาท/เดือน (`FR-DOR-12`, `ASM-16`, `ASM-17`)
3. ตรวจข้อมูลจำเป็นและตรวจไฟล์รูปภาพตามประเภท ขนาด และจำนวน โดยปฏิเสธเฉพาะไฟล์ที่ไม่ผ่านเงื่อนไข (`CON-DATA-01`, `CON-FILE-01`, `FR-DOR-13`, `FR-DOR-14`, `FR-DOR-17`, `FR-DOR-18`)
4. บันทึกข้อมูลก่อนแสดงเป็นข้อมูลล่าสุด; เก็บข้อมูลที่ยังไม่กดบันทึกไว้ในฟอร์มเท่านั้น และไม่สร้างสถานะ Draft (`CON-BUS-01`, `FR-DOR-15`, `FR-DOR-16`, `ASM-12`, `ASM-19`)
5. แสดงสถานะรออนุมัติแก่เจ้าของหอพัก; Admin ตรวจสอบข้อมูลผ่าน UC-13 ที่มีอยู่; ผู้ใช้งานทั่วไปเห็นเฉพาะข้อมูลที่อนุมัติแล้ว โดยเชื่อมต่อมุมมองเดิมและไม่สร้าง workflow อนุมัติใน UC-03 (`DOM-RULE-01`, `FR-DOR-15`, `NFR-DATA-02`, `AC-DOR-08`, `AC-DOR-12`; UC-13 อยู่นอกขอบเขต)

| กลไกยืนยันตัวตนที่มีอยู่ | `CON-ACC-01`, `CON-AUTH-01` | ต้องใช้ตัวตนเจ้าของหอพักที่เข้าสู่ระบบในการตรวจสิทธิ์; spec ไม่ได้กำหนดวิธีหรือเทคโนโลยียืนยันตัวตน; ทีมตัดสินใจ (2569-11-13): ระหว่างที่ 007 login ยังไม่มีโค้ด ใช้ตัวตนจำลองสำหรับ prototype ผ่าน header X-Owner-Id อ่านในฟังก์ชัน get_current_owner() ฟังก์ชันเดียว ทุก API ของ 003 ใช้ฟังก์ชันนี้; ไม่มี header = ปฏิเสธ; ข้อมูลตัวอย่างใช้ owner-1, owner-2 ให้ตรงกับ 005; เมื่อ 007 เสร็จให้เปลี่ยนเฉพาะ get_current_owner() |

## 3. โมเดลข้อมูล

| Entity / ข้อมูล | ฟิลด์หลักที่ระบุในแผน | รองรับ |
|---|---|---|
| บัญชีเจ้าของหอพัก (อ้างอิงบัญชีที่เข้าสู่ระบบ ไม่สร้างโมเดลบัญชีซ้ำ) | `owner_id` สำหรับเชื่อมกับหอพัก | `CON-ACC-01`, `CON-AUTH-01`, `FR-DOR-09`, `ASM-07` |
| `Dormitory` | `dormitory_id` (รหัสระบบแก้ไขไม่ได้), `owner_id`, ชื่อ, ที่อยู่/ทำเล, ประเภท, สิ่งอำนวยความสะดวก (optional), กฎระเบียบ (optional), ช่องทางติดต่อ (required), สถานะอนุมัติที่ระบบเดิมจัดการ | `CON-DATA-01`, `CON-AUTH-01`, `FR-DOR-09` ถึง `FR-DOR-12`, `FR-DOR-15`, `ASM-11`, `ASM-13`, `ASM-15` |
| `DormitoryRoom` | `room_id`, `dormitory_id`, ราคาค่าเช่าต่อห้องต่อเดือน (บาท/เดือน); รายละเอียดอื่นให้จำกัดตามข้อกำหนดที่มีอยู่ ไม่กำหนดฟิลด์เพิ่มเติมในแผนนี้ | `CON-DATA-01`, `FR-DOR-12`, `ASM-16`, `ASM-17` |
| รูปภาพหอพัก/ห้องพัก | `image_id`, ความสัมพันธ์กับหอพักหรือห้องพักเจ้าของภาพ, ไฟล์รูปภาพ, ประเภทไฟล์, ขนาดไฟล์ และสถานะอนุมัติรายรูป; รูปใหม่เริ่มสถานะ “รออนุมัติ”; จำกัดไม่เกิน 10 รูปแยกต่อหอพักและต่อห้องพัก | `CON-FILE-01`, `FR-DOR-14`, `FR-DOR-18`, `NFR-DATA-02`, `AC-DOR-12`, `ASM-08` |

กติกาข้อมูล:

- หอพักต้องเชื่อมกับบัญชีเจ้าของหอพักที่เข้าสู่ระบบ และการอ่าน/แก้ไขต้องตรวจเจ้าของข้อมูลทุกครั้ง (`CON-ACC-01`, `CON-AUTH-01`, `NFR-SEC-02`)
- ฟิลด์บังคับของข้อมูลหอพักคือชื่อหอพัก ที่อยู่/ทำเล ประเภทหอพัก และช่องทางติดต่อ; สิ่งอำนวยความสะดวก กฎระเบียบ และรูปภาพเป็น optional (`CON-DATA-01`, `FR-DOR-10`, `ASM-15`)
- ราคาต่อห้องต่อเดือนเป็นข้อมูลจำเป็นของห้องพักและกำหนดหลังบันทึกหอพักสำเร็จในหน้าจัดการข้อมูลห้องพักที่แยกต่างหาก (`CON-DATA-01`, `FR-DOR-12`, `ASM-16`, `ASM-17`)
- หนึ่งหอพักเชื่อมโยงกับห้องพักได้หลายห้อง และการจัดการข้อมูลห้องพักใช้หน้าจอแยก (`FR-DOR-12`, `ASM-17`)
- การตรวจสิทธิ์จัดการห้องพักต้องตรวจว่า `dormitoryId` เป็นของเจ้าของที่เข้าสู่ระบบ และ `roomId` ที่ร้องขอเป็นห้องภายใต้ `dormitoryId` นั้นจริง ทั้งการอ่านและแก้ไข (`CON-AUTH-01`, `NFR-SEC-02`, `FR-DOR-12`, `ASM-17`)
- รูปภาพแต่ละรายการเชื่อมกับหอพักหรือห้องพักที่เป็นเจ้าของภาพ; จำกัดสูงสุด 10 รูปนับแยกสำหรับแต่ละหอพักและแต่ละห้องพัก (`CON-FILE-01`, `FR-DOR-14`, `ASM-08`)
- รหัสหอพักและข้อมูลที่ระบบสร้างอัตโนมัติแก้ไขไม่ได้ (`FR-DOR-12`, `ASM-13`)
- สถานะอนุมัติหอพักอ่าน/แสดงจากกระบวนการที่มีอยู่; รูปแต่ละรูปมีสถานะแยกกันและรูปใหม่เริ่ม “รออนุมัติ”; มุมมองสาธารณะแสดงเฉพาะหอพักและรูปที่อนุมัติแล้ว โดยแผนนี้ไม่สร้าง workflow อนุมัติของ Admin (`DOM-RULE-01`, `FR-DOR-15`, `NFR-DATA-02`, `AC-DOR-12`, `ASM-09`, Out of scope UC-13)
- ไฟล์ที่ไม่ผ่านเงื่อนไขหรือทำให้เกินจำนวนที่อนุญาตถูกปฏิเสธเป็นรายไฟล์ ส่วนไฟล์ที่ผ่านเงื่อนไขรับต่อได้; ไม่กำหนดรูปแบบข้อมูลหรือฟิลด์อื่นนอกเหนือจาก spec (`CON-FILE-01`, `FR-DOR-14`, `FR-DOR-18`, `ASM-18`)
- ข้อมูลที่ยังไม่กดบันทึกอยู่ใน state ของฟอร์มเท่านั้น ไม่สร้าง Draft และไม่แสดงเป็นข้อมูลล่าสุด (`CON-BUS-01`, `FR-DOR-16`, `ASM-12`, `ASM-19`)

## 4. API / หน้าจอ

ชื่อ path เป็นสัญญาเชิงตรรกะสำหรับวางแผน ยังไม่ใช่ข้อกำหนดเทคโนโลยีหรือ implementation

|---|---|---|---|
| `GET /owners/dormitories` | ตัวตนเจ้าของหอพักจากการยืนยันตัวตน | รายการหอพักของเจ้าของที่เข้าสู่ระบบ พร้อมข้อมูลที่จำเป็นต่อปุ่มเพิ่ม/แก้ไข | `CON-ACC-01`, `CON-AUTH-01`, `FR-DOR-09`, `AC-DOR-07` |
| `POST /owners/dormitories` | ข้อมูลบังคับและ optional ของหอพัก โดยไม่มีราคาห้องพัก | ผล validation และข้อมูลที่บันทึกแล้ว; ข้อมูลล่าสุดที่เจ้าของหอพัก/Admin ดูได้ตามสถานะ | `CON-DATA-01`, `CON-BUS-01`, `FR-DOR-10`, `FR-DOR-13`, `FR-DOR-15`, `FR-DOR-17` |

| `PUT /owners/dormitories/{dormitoryId}` | รหัสหอพักและเฉพาะฟิลด์หอพักที่แก้ไขได้ | ผล validation และข้อมูลล่าสุดที่บันทึกสำเร็จ | `CON-AUTH-01`, `CON-DATA-01`, `CON-BUS-01`, `FR-DOR-12`, `FR-DOR-13`, `FR-DOR-15`, `FR-DOR-17` |
| `GET /owners/dormitories/{dormitoryId}/rooms` | รหัสหอพักและตัวตนเจ้าของจากการยืนยันตัวตน | รายการห้องพักที่เชื่อมกับหอพักที่มีสิทธิ์; ตรวจสิทธิ์ของ `dormitoryId` ก่อนคืนข้อมูล | `CON-AUTH-01`, `NFR-SEC-02`, `FR-DOR-12`, `ASM-17` |
| `POST /owners/dormitories/{dormitoryId}/rooms` | รหัสหอพักและข้อมูลห้องพักใหม่ รวมราคาต่อเดือน | ผล validation และข้อมูลห้องพักที่บันทึกสำเร็จ | `CON-AUTH-01`, `CON-DATA-01`, `CON-BUS-01`, `FR-DOR-12`, `FR-DOR-15`, `ASM-16`, `ASM-17` |
| `PUT /owners/dormitories/{dormitoryId}/rooms/{roomId}` | รหัสหอพัก/ห้องพักและข้อมูลห้องพักที่แก้ไขได้ รวมราคาต่อเดือน | ผล validation และข้อมูลห้องพักที่บันทึกสำเร็จ; ตรวจว่าหอพักเป็นของเจ้าของและห้องอยู่ใต้หอพักนั้น | `CON-AUTH-01`, `NFR-SEC-02`, `CON-DATA-01`, `CON-BUS-01`, `FR-DOR-12`, `FR-DOR-15`, `ASM-16`, `ASM-17` |
| `POST /owners/dormitories/{dormitoryId}/images` และ `POST /owners/dormitories/{dormitoryId}/rooms/{roomId}/images` | รูปภาพหอพักหรือห้องพักที่เลือก | ผลรายไฟล์ว่าอัปโหลดสำเร็จหรือถูกปฏิเสธพร้อมสาเหตุ; ตรวจเจ้าของ `dormitoryId` และตรวจว่า `roomId` อยู่ใต้หอพักนั้นก่อนอัปโหลดรูปห้อง | `CON-AUTH-01`, `NFR-SEC-02`, `CON-FILE-01`, `FR-DOR-14`, `FR-DOR-18`, `AC-DOR-10` |
| `GET /owners/dormitories/{dormitoryId}/images` และ `GET /owners/dormitories/{dormitoryId}/rooms/{roomId}/images` | รหัสหอพัก/ห้องพักและตัวตนเจ้าของ | รายการรูปที่บันทึกแล้วของเป้าหมาย โดยตรวจสิทธิ์เจ้าของและความสัมพันธ์ห้องพัก | `CON-AUTH-01`, `CON-FILE-01`, `FR-DOR-12` |

| หน้ารายการหอพัก | เจ้าของหอพักที่เข้าสู่ระบบ | เฉพาะรายการหอพักของเจ้าของ พร้อมทางเลือกเพิ่ม/แก้ไข | `CON-ACC-01`, `CON-AUTH-01`, `FR-DOR-09`, `AC-DOR-07` |
| ฟอร์มเพิ่ม/แก้ไขหอพัก | ข้อมูลหอพัก รูปที่เลือก และรูปเดิมที่บันทึกแล้ว | ข้อผิดพลาดรายช่องหรือผลบันทึก; แสดง/ลบรูปเดิมและอัปโหลดรูปทดแทน โดยยกเลิกข้อมูลฟอร์มที่ยังไม่บันทึกตามเดิม | `CON-DATA-01`, `CON-BUS-01`, `CON-FILE-01`, `FR-DOR-10` ถึง `FR-DOR-18`, `AC-DOR-08` ถึง `AC-DOR-11` |
| หน้าจัดการข้อมูลห้องพัก (แยกจากหน้าหอพัก) | หอพักที่เลือกและข้อมูลห้องพัก | รายการห้องที่เชื่อมโยงกับหอพัก; แสดง/ลบรูปเดิมและอัปโหลดรูปทดแทนของแต่ละห้อง | `CON-AUTH-01`, `CON-FILE-01`, `FR-DOR-12`, `AC-DOR-08`, `ASM-17` |
| มุมมองรายละเอียด Admin ที่มีอยู่ (เชื่อมต่อเท่านั้น) | หอพักที่อยู่ในขอบเขตการตรวจของ Admin | ข้อมูลและสถานะ “รออนุมัติ”; ไม่สร้างขั้นตอนอนุมัติใหม่ | `DOM-RULE-01`, `FR-DOR-15`, `ASM-09`, `ASM-14`; UC-13 เป็น Out of scope |
| มุมมองรายละเอียดสาธารณะที่มีอยู่ (เชื่อมต่อเท่านั้น) | รหัสหอพัก | อ่านข้อมูลหอพักที่เจ้าของบันทึกผ่าน UC-03 และแสดงเมื่อหอพักอนุมัติแล้ว; แสดงเฉพาะรูปที่อนุมัติแล้วและไม่เปิดรูปที่รออนุมัติ; ไม่สร้างการค้นหาสาธารณะ | `NFR-DATA-02`, `AC-DOR-12`; UC-01 เป็น Out of scope |

การยกเลิกเป็นการทิ้ง state ที่ยังไม่บันทึกและกลับไปหน้ารายการ/ข้อมูลเดิม โดยไม่เรียก API เพื่อบันทึกการยกเลิก (`FR-DOR-16`, `ASM-19`).

ทีมเลือกแนวทาง B: เจ้าของหอพักบันทึกข้อมูลหอพักโดยไม่ต้องกรอกราคาห้องพักก่อน เมื่อบันทึกสำเร็จจึงเพิ่มข้อมูลห้องพักและกำหนดราคาต่อห้องต่อเดือนผ่านหน้าจอจัดการห้องพักที่แยกต่างหาก (`CON-DATA-01`, `FR-DOR-10`, `FR-DOR-12`, `ASM-15` ถึง `ASM-17`). ราคายังคงเป็นข้อมูลจำเป็นของแต่ละห้องพัก; ไม่ได้เพิ่ม requirement นอกเหนือจากการปรับความหมายของฟิลด์บังคับให้ตรงกับการตัดสินใจนี้

## 7. ลำดับงาน

1. ยืนยันสัญญาข้อมูลหอพัก/ห้องพักจากฟิลด์ที่ spec ระบุ โดยไม่เพิ่มฟิลด์ห้องพักที่ไม่มีข้อกำหนด (`CON-DATA-01`, `FR-DOR-10`, `FR-DOR-12`, `ASM-15` ถึง `ASM-17`)
2. เชื่อมตัวตนเจ้าของหอพักและสร้างรายการ/รายละเอียดหอพักที่กรองสิทธิ์เจ้าของ (`CON-ACC-01`, `CON-AUTH-01`, `FR-DOR-09`, `FR-DOR-11`, `NFR-SEC-02`)
3. ทำฟอร์มเพิ่ม/แก้ไขหอพักและตรวจข้อมูลบังคับแบบรายช่อง (`CON-DATA-01`, `FR-DOR-10`, `FR-DOR-13`, `FR-DOR-17`)
4. ทำหน้าจัดการห้องพักแยก เชื่อมกับหอพักที่เลือก และรองรับราคาต่อห้องต่อเดือน (`FR-DOR-12`, `ASM-16`, `ASM-17`)
5. ทำการอัปโหลดรูปพร้อมตรวจชนิด ขนาด จำนวน และผลรายไฟล์ โดยคงไฟล์ที่ถูกต้อง (`CON-FILE-01`, `FR-DOR-14`, `FR-DOR-18`)
6. ทำการบันทึกและยกเลิก: แสดงข้อมูลล่าสุดหลังบันทึกสำเร็จ และทิ้งค่าที่ยังไม่บันทึกเมื่อยกเลิก (`CON-BUS-01`, `FR-DOR-15`, `FR-DOR-16`, `ASM-12`, `ASM-19`)
7. เชื่อมการแสดงข้อมูลตามสถานะกับมุมมอง Admin/สาธารณะที่มีอยู่ โดยไม่สร้าง workflow อนุมัติหรือการค้นหาสาธารณะ (`DOM-RULE-01`, `FR-DOR-15`, `NFR-DATA-02`, `AC-DOR-12`, UC-01/UC-13 Out of scope)
8. รันทดสอบ `AC-DOR-07` ถึง `AC-DOR-12` รวมกรณีข้อมูลไม่ถูกต้อง ยกเลิก ข้อมูลรออนุมัติไม่แสดงต่อสาธารณะ และตรวจสิทธิ์ทั้ง `dormitoryId`/`roomId` ตาม `NFR-SEC-02` (`CON-AUTH-01`)
9. ดำเนิน usability testing ตามเกณฑ์ `NFR-USE-02`: success rate อย่างน้อย 90% แบบไม่ต้องได้รับความช่วยเหลือ ไม่มีข้อผิดพลาดร้ายแรง และบันทึกสถิติที่กำหนด

## 8. สิ่งที่ยังไม่ทำ / ข้อสรุปและข้อตัดสินใจ

* Q-01 NFR-USE-02 ได้รับคำตอบแล้วและถูกบันทึกไว้ใน spec.md: ผู้ใช้งานอย่างน้อย 90% ของผู้ทดสอบต้องสามารถเพิ่มหรือแก้ไขข้อมูลหอพักได้สำเร็จโดยไม่ต้องได้รับความช่วยเหลือจากผู้อื่น และไม่เกิดข้อผิดพลาดร้ายแรงที่ส่งผลต่อข้อมูลหรือการทำงาน รูปแบบการทดสอบคือ usability testing ตามที่ระบุไว้ใน spec; แผนนี้ใช้เกณฑ์นี้เป็นมาตรฐานตรวจสอบ

แนวทางที่ทีมตัดสินใจแล้วสำหรับ design gap (ไม่สร้าง ID ใหม่):

- ใช้แนวทาง B: ให้เจ้าของหอพักสร้างข้อมูลหอพักก่อน; หลังจากสร้างหอพักสำเร็จแล้ว จึงเข้าไปเพิ่มข้อมูลห้องพักและกำหนดราคาต่อห้องในหน้าจัดการห้องพัก
- การจัดการข้อมูลหอพักและข้อมูลห้องพักยังคงแยกหน้าต่างกันชัดเจนตาม `FR-DOR-12`
- ไม่สร้าง requirement ใหม่หรือ API แยกเฉพาะสำหรับราคา; การกำหนดราคาเป็นส่วนหนึ่งของการเพิ่มข้อมูลห้องพักผ่านหน้าจอจัดการห้องพักตาม `FR-DOR-12` โดยใช้สัญญาเชิงตรรกะในแผนนี้

สิ่งที่อยู่นอกขอบเขตของแผนนี้และจะไม่สร้าง:

- การค้นหาและดูข้อมูลหอพักของผู้ใช้งานทั่วไป (UC-01); ใช้เฉพาะการเชื่อมต่อข้อมูลที่จำเป็นต่อ `AC-DOR-12`
- การนัดหมายเพื่อดูห้องพัก (UC-06)
- การจองห้องพัก (UC-12)
- workflow ตรวจสอบและอนุมัติข้อมูลหอพักโดย Admin (UC-13); ใช้เฉพาะข้อมูลสถานะ/มุมมองที่มีอยู่
- การจัดการข้อมูลหอพักของเจ้าของหอพักรายอื่น
