# แผนทางเทคนิค: เข้าสู่ระบบ

ไฟล์ข้อกำหนดอ้างอิง: [spec.md](./spec.md)

Spec ID: `SPEC-LOGIN-001` | สถานะข้อกำหนด: `Draft v2`

## 1. สรุปแนวทาง

1. ให้ผู้ใช้ที่มีบัญชีเข้าสู่ระบบด้วย username/email และ password ตาม `FR-LOGIN-01`
2. ตรวจสอบข้อมูลบัญชีและสถานะก่อนสร้าง session ตาม `FR-LOGIN-02`, `FR-LOGIN-03` และ Constraints ที่เกี่ยวข้อง
3. เมื่อเข้าสู่ระบบสำเร็จ สร้าง session และกำหนด role ตาม `FR-LOGIN-04`, `FR-LOGIN-05`
4. แสดงข้อความผิดพลาด/ช่องทางช่วยเหลือ และลิงก์ไปยัง flow สมัครสมาชิกหรือลืมรหัสผ่านตาม `FR-LOGIN-06` ถึง `FR-LOGIN-08`
5. ป้องกันฟังก์ชันที่ต้อง Login และทดสอบทุก AC; รายละเอียดที่ยังไม่ชัดให้คงรอคำตอบตาม Open Questions

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| React (Vite) | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้สร้างหน้า Login; spec ไม่ระบุเทคโนโลยีหน้าบ้าน |
| Python FastAPI | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้ทำ API ตรวจสอบข้อมูล Login และ session; spec ไม่ระบุเทคโนโลยีหลังบ้าน |
| ฐานข้อมูลเชิงสัมพันธ์ | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้เก็บบัญชีและข้อมูล role/status; โครงสร้างจริงยืนยันกับ stack ของทีม |
| กลไก session/authentication | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้สร้างและตรวจ session ตาม `FR-LOGIN-04`, `FR-LOGIN-09`; รายละเอียด status ที่ต้องบันทึกรอ `Q-02` |
| HTTPS/TLS 1.2 ขึ้นไป | `CON-SEC-02`, `NFR-SEC-02` | ป้องกันข้อมูล Login ระหว่าง Browser กับระบบ |
| เครื่องมือทดสอบของ stack | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้ทดสอบ AC และข้อกำหนดด้าน security/performance |

> เทคโนโลยีที่ไม่ได้ระบุใน Constraints เป็นเพียงแนวทางที่ทีมเลือกเอง และเปลี่ยนได้ตาม stack จริง

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับ |
|---|---|---|
| `User` | `id`, `username`, `email`, `password_hash`, `role`, `account_status` | `FR-LOGIN-01`, `FR-LOGIN-02`, `FR-LOGIN-03`, `FR-LOGIN-05` |
| `Session` | `id`, `user_id` | `FR-LOGIN-04`, `FR-LOGIN-09` |

กติกาข้อมูล:

- ห้ามเก็บ password เป็น plain text; การจัดเก็บต้องเป็นไปตาม `CON-SEC-01` และ `NFR-SEC-01`
- ตรวจสอบบัญชีและสถานะก่อนสร้าง session ตาม `CON-LOGIN-01`, `CON-LOGIN-02`
- ใช้ role ที่ผูกกับบัญชีเพื่อกำหนดสิทธิ์ตาม `CON-LOGIN-03`
- ความหมายและข้อมูลที่ต้องบันทึกเป็น “สถานะการเข้าสู่ระบบ” ยังไม่ระบุ จึงยังไม่กำหนดฟิลด์เพิ่มจนกว่าจะได้คำตอบ `Q-02`

## 4. API / หน้าจอ

| รายการ | Input หลัก | Output หลัก | รองรับ |
|---|---|---|---|
| `POST /login` | `username_or_email`, `password` | ผลตรวจสอบ, session เมื่อสำเร็จ, role สำหรับกำหนดหน้าแรก; ข้อความและช่องทางติดต่อเมื่อบัญชีถูกระงับ | `FR-LOGIN-01` ถึง `FR-LOGIN-06` |
| หน้า Login | username/email, password | สถานะการเข้าสู่ระบบ, ข้อความแจ้งเตือน, ลิงก์สมัครสมาชิกและลืมรหัสผ่าน | `FR-LOGIN-01`, `FR-LOGIN-06` ถึง `FR-LOGIN-08`, `NFR-USE-01` |
| Session Guard | session | อนุญาตหรือปฏิเสธการเข้าถึงและนำผู้ไม่มี session ไปหน้า Login | `FR-LOGIN-09` |
| การนำทางหลัง Login | session, role | หน้าแรกตามสิทธิ์ role; รายละเอียดหน้าเป้าหมายรอ `Q-01` | `FR-LOGIN-05` |
| ลิงก์สมัครสมาชิก | - | นำไปยัง flow สมัครสมาชิกที่กำหนดไว้ | `FR-LOGIN-07` |
| ลิงก์ลืมรหัสผ่าน | - | นำไปยัง flow รีเซ็ตรหัสผ่านที่กำหนดไว้ | `FR-LOGIN-08` |

แนวทางการทำงาน:

1. รับ username/email และ password
2. ตรวจข้อมูลบัญชีและ password; เมื่อไม่ถูกต้องให้แสดงข้อความทั่วไปโดยไม่ระบุช่องที่ผิด (`FR-LOGIN-02`, `FR-LOGIN-06`, `NFR-SEC-03`)
3. ตรวจสถานะบัญชีก่อนสร้าง session; หากถูกระงับ ให้ปฏิเสธ แจ้งสถานะ และแสดงช่องทางติดต่อผู้ดูแลระบบ (`FR-LOGIN-03`)
4. เมื่อผ่านการตรวจสอบ สร้าง session และใช้ role นำทางไปหน้าแรกตามสิทธิ์ (`FR-LOGIN-04`, `FR-LOGIN-05`)
5. ตรวจ session ก่อนเข้าฟังก์ชันที่กำหนดให้ต้อง Login (`FR-LOGIN-09`); รายการฟังก์ชันรอ `Q-02`

> ชื่อ API และรายละเอียด input/output เป็นแนวทางสำหรับการวางแผน ไม่ใช่ข้อกำหนดเพิ่มเติมจาก spec

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| `CON-ACC-01` | โมเดล `User` และขั้นตรวจบัญชีก่อน Login ในหัวข้อ 3–4 | ใช้แล้ว |
| `CON-LOGIN-01` | ตรวจข้อมูลบัญชีก่อนสร้าง session ในหัวข้อ 3–4 | ใช้แล้ว |
| `CON-LOGIN-02` | ตรวจ `account_status` ก่อนสร้าง session ในหัวข้อ 3–4 | ใช้แล้ว |
| `CON-LOGIN-03` | ใช้ role จากบัญชีกำหนดสิทธิ์ในหัวข้อ 3–4 | ใช้แล้ว |
| `CON-SEC-01` | ห้ามเก็บ password แบบ plain text ในหัวข้อ 2–3 | ใช้แล้ว |
| `CON-SEC-02` | กำหนด HTTPS/TLS สำหรับการรับส่ง Login ในหัวข้อ 2 | ใช้แล้ว |
| `CON-UI-01` | วางหน้า Login ให้รองรับอุปกรณ์ แต่ยังระบุอุปกรณ์ที่ต้องรองรับไม่ได้ | ยังไม่ได้ใช้ครบ เพราะรอคำตอบ `Q-03` |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| `AC-LOGIN-01` | `test_AC_LOGIN_01_valid_credentials` | เตรียมบัญชีที่ใช้งานได้ กรอก username/email และ password ที่ถูกต้อง แล้วตรวจว่าระบบอนุญาตให้ Login และสร้าง session |
| `AC-LOGIN-02` | `test_AC_LOGIN_02_redirect_by_role` | Login ด้วยบัญชีแต่ละ role แล้วตรวจการนำทางไปหน้าแรกตามสิทธิ์; หน้าเป้าหมายที่แน่นอนรอ `Q-01` |
| `AC-LOGIN-03` | `test_AC_LOGIN_03_invalid_credentials` | ใช้ username/email หรือ password ที่ไม่ถูกต้อง ตรวจว่าไม่มี session และข้อความไม่ระบุว่าข้อมูลส่วนใดผิด |
| `AC-LOGIN-04` | `test_AC_LOGIN_04_suspended_account` | ใช้บัญชีที่ถูกระงับ ตรวจว่าไม่มี session และแสดงข้อความแจ้งสถานะพร้อมช่องทางติดต่อผู้ดูแลระบบ |
| `AC-LOGIN-05` | `test_AC_LOGIN_05_registration_link` | เลือกลิงก์สมัครสมาชิกและตรวจว่านำไปยัง flow สมัครสมาชิก |
| `AC-LOGIN-06` | `test_AC_LOGIN_06_password_reset_link` | เลือกลิงก์ลืมรหัสผ่านและตรวจว่านำไปยัง flow รีเซ็ตรหัสผ่าน |
| `AC-LOGIN-07` | `test_AC_LOGIN_07_session_required` | ไม่มี session แล้วเข้าฟังก์ชันที่กำหนดให้ต้อง Login; ตรวจว่าถูกปฏิเสธและนำไปหน้า Login; รายการฟังก์ชันรอ `Q-02` |
| `AC-LOGIN-08` | `test_AC_LOGIN_08_login_response_under_two_seconds` | วัดเวลาตอบสนองคำขอ Login และตรวจเกณฑ์ไม่เกิน 2 วินาที; เงื่อนไขการวัดรอ `Q-04` |

การตรวจ `NFR-SEC-01`, `NFR-SEC-02` และ `CON-SEC-01` ต้องตรวจการจัดเก็บ password และการรับส่งผ่าน HTTPS/TLS จากระบบจริง; หลักฐานตรวจรับรอ `Q-05` ไม่สรุปจาก mock เพียงอย่างเดียว

## 7. ลำดับงาน

1. ยืนยัน Open Questions ที่กระทบ role, session, UI, performance และ security ก่อนปิดรายละเอียดที่เกี่ยวข้อง (`Q-01` ถึง `Q-05`)
2. เตรียมโมเดลบัญชีและกลไกปกป้อง password (`FR-LOGIN-01` ถึง `FR-LOGIN-03`, `CON-ACC-01`, `CON-SEC-01`)
3. สร้าง API รับข้อมูล Login และตรวจสอบบัญชีกับ password (`FR-LOGIN-01`, `FR-LOGIN-02`)
4. ตรวจสถานะบัญชีและจัดการกรณีบัญชีถูกระงับ (`FR-LOGIN-03`, `AC-LOGIN-04`)
5. สร้าง session หลังตรวจสอบผ่านและกำหนด role (`FR-LOGIN-04`, `FR-LOGIN-05`, `AC-LOGIN-01`, `AC-LOGIN-02`)
6. ทำข้อความผิดพลาดและลิงก์ไปยัง flow สมัครสมาชิก/ลืมรหัสผ่าน (`FR-LOGIN-06` ถึง `FR-LOGIN-08`, `AC-LOGIN-03`, `AC-LOGIN-05`, `AC-LOGIN-06`)
7. เพิ่ม Session Guard และหน้า Login ให้ตรงกับขอบเขตที่ทีมยืนยัน (`FR-LOGIN-09`, `NFR-USE-01`, `CON-UI-01`, `AC-LOGIN-07`)
8. ตรวจ Constraints และทดสอบ AC ทั้งหมด รวม security และ performance ตามคำตอบของทีม (`AC-LOGIN-01` ถึง `AC-LOGIN-08`, `CON-SEC-02`, `NFR-PERF-01`, `NFR-SEC-01` ถึง `NFR-SEC-03`)

## 8. สิ่งที่ยังไม่ทำ

- `Q-01` Guest เป็น role ที่มีบัญชีและเข้าสู่ระบบได้หรือหมายถึงผู้เยี่ยมชมที่ยังไม่เข้าสู่ระบบ และหน้าแรกของแต่ละ role คือหน้าใด (ทีมผู้กำหนด UC-07) — ส่วนการกำหนด role และปลายทางที่เกี่ยวข้องจะยังไม่สรุปจนกว่าจะได้คำตอบ
- `Q-02` “บันทึกสถานะการเข้าสู่ระบบ” ใน FR-LOGIN-04 ต้องบันทึกข้อมูลใด และฟังก์ชันใดบ้างที่ FR-LOGIN-09 กำหนดให้ต้องมี session (ทีมผู้กำหนด UC-07 และ Use Case ที่เกี่ยวข้อง) — ส่วนข้อมูลที่บันทึกและขอบเขต Session Guard จะยังไม่กำหนดจนกว่าจะได้คำตอบ
- `Q-03` เกณฑ์ประเมิน NFR-USE-01 และอุปกรณ์ที่รองรับตาม CON-UI-01 คืออะไร (ทีมเอง) — ส่วนเกณฑ์ประเมินและรายการอุปกรณ์จะยังไม่กำหนดจนกว่าจะได้คำตอบ
- `Q-04` สภาวะเครือข่ายปกติและจุดเริ่ม/หยุดวัดเวลาตาม NFR-PERF-01 คืออะไร (ทีมเอง) — ส่วนเงื่อนไขทดสอบ performance จะยังไม่กำหนดจนกว่าจะได้คำตอบ
- `Q-05` ใช้หลักฐานใดตรวจรับการปกป้อง password ตาม NFR-SEC-01 และการเข้ารหัสการรับส่งตาม NFR-SEC-02 (ทีมเอง) — ส่วนเกณฑ์หลักฐานตรวจรับ security จะยังไม่กำหนดจนกว่าจะได้คำตอบ

ฟังก์ชันสมัครสมาชิกโดยละเอียด, รีเซ็ตรหัสผ่านโดยละเอียด และการจัดการสิทธิ์เชิงลึกยังอยู่นอกขอบเขต UC-07 ตาม `spec.md`
