# แผนทางเทคนิค: เข้าสู่ระบบ

ไฟล์ข้อกำหนดอ้างอิง: `spec.md`

Spec ID: `SPEC-LOGIN-001` | สถานะข้อกำหนด: `Draft v2`

## 1. สรุปแนวทาง

1. สร้างหน้าเข้าสู่ระบบสำหรับ Guest, Resident, Dormitory Owner และ Admin ตาม `FR-LOGIN-01`
2. รับชื่อผู้ใช้หรืออีเมลและรหัสผ่าน แล้วตรวจสอบข้อมูลกับบัญชีที่ลงทะเบียนไว้ตาม `FR-LOGIN-02`
3. ตรวจสอบสถานะบัญชีก่อนสร้าง session หากบัญชีถูกระงับต้องไม่สามารถเข้าสู่ระบบได้ตาม `FR-LOGIN-03`
4. เมื่อ authentication สำเร็จ ให้สร้าง session ตาม `FR-LOGIN-04`
5. ตรวจสอบ role และนำผู้ใช้ไปยังหน้าที่เหมาะสมตาม `FR-LOGIN-05`
6. แสดงข้อความผิดพลาดแบบทั่วไปเมื่อข้อมูล Login ไม่ถูกต้องตาม `FR-LOGIN-06`
7. รองรับช่องทางสมัครสมาชิกและลืมรหัสผ่านตาม `FR-LOGIN-07` และ `FR-LOGIN-08`
8. ตรวจสอบ session ก่อนอนุญาตให้เข้าถึงฟังก์ชันที่ต้อง Login ตาม `FR-LOGIN-09`
9. วางแผนทดสอบ Acceptance Criteria ทั้งหมด รวมถึง performance และ security requirements

## 3. โมเดลข้อมูล

| Entity | ฟิลด์หลัก | รองรับ |
|---|---|---|
| `User` | `id`, `username`, `email`, `password_hash`, `role`, `account_status` | `FR-LOGIN-01`, `FR-LOGIN-02`, `FR-LOGIN-03`, `FR-LOGIN-05` |
| `Session` | `id`, `user_id`, `created_at`, `expires_at` | `FR-LOGIN-04`, `FR-LOGIN-09` |
| `LoginAttempt` | `id`, `user_id`, `attempted_at`, `result` | รองรับการตรวจสอบเหตุการณ์ Login และความปลอดภัย |

กติกาข้อมูล:

- รหัสผ่านต้องไม่ถูกจัดเก็บเป็น plain text
- ต้องจัดเก็บรหัสผ่านในรูปแบบที่ปลอดภัยตามแนวทางของระบบ
- ระบบต้องตรวจสอบบัญชีก่อนสร้าง session
- ระบบต้องตรวจสอบ `account_status` ก่อนสร้าง session
- ระบบต้องใช้ `role` เพื่อกำหนดสิทธิ์และการนำทาง
- เมื่อเข้าสู่ระบบสำเร็จต้องสร้าง session ที่เชื่อมโยงกับ `user_id`
- หากข้อมูล Login ไม่ถูกต้อง ต้องแสดงข้อความทั่วไปโดยไม่ระบุว่าข้อมูลส่วนใดผิด

## 4. API / หน้าจอ

| รายการ | Input หลัก | Output หลัก | รองรับ |
|---|---|---|---|
| `POST /login` | `username_or_email`, `password` | ผลการ authentication และข้อมูล role ที่จำเป็น | `FR-LOGIN-01`, `FR-LOGIN-02`, `FR-LOGIN-03`, `FR-LOGIN-04`, `FR-LOGIN-05` |
| หน้าล็อกอิน | username/email, password | สถานะ Login และข้อความแจ้งเตือน | `FR-LOGIN-01`, `NFR-USE-01` |
| Session Guard / Authentication Middleware | session | อนุญาตหรือปฏิเสธการเข้าถึง | `FR-LOGIN-09` |
| หน้าหลักหลัง Login | session, role | หน้าที่ตรงกับสิทธิ์ของผู้ใช้ | `FR-LOGIN-05` |
| ลิงก์สมัครสมาชิก | - | นำไปยัง flow สมัครสมาชิก | `FR-LOGIN-07` |
| ลิงก์ลืมรหัสผ่าน | - | นำไปยัง flow รีเซ็ตรหัสผ่าน | `FR-LOGIN-08` |

แนวทางการทำงานของ Login:

1. รับ username/email และ password
2. ตรวจสอบข้อมูลบัญชี
3. ตรวจสอบสถานะบัญชี
4. ตรวจสอบ password
5. หากผ่านการตรวจสอบ ให้สร้าง session
6. อ่าน role ของผู้ใช้
7. นำผู้ใช้ไปยังหน้าที่ตรงกับ role

แนวทางการตรวจสอบ Session:

1. ตรวจสอบว่าผู้ใช้มี session ที่ใช้งานได้หรือไม่
2. หากไม่มี session ให้ปฏิเสธการเข้าถึงฟังก์ชันที่ต้อง Login
3. นำผู้ใช้ไปยังหน้า Login
4. หากมี session ให้ดำเนินการตรวจสอบสิทธิ์ตาม role ต่อไป

> หมายเหตุ: ชื่อ API และ field เป็นแนวทางสำหรับการวางแผนเท่านั้น รายละเอียดจริงต้องยืนยันก่อน implementation

## 6. แผนทดสอบจาก Acceptance Criteria

| `AC-LOGIN-02` | `test_AC_LOGIN_02_redirect_by_role` | เตรียมบัญชีแต่ละ role แล้ว Login ตรวจว่าระบบนำทางไปยังหน้าที่ตรงกับ role |

| `AC-LOGIN-08` | `test_AC_LOGIN_08_login_response_under_two_seconds` | ส่งคำขอ Login ภายใต้สภาวะปกติและตรวจเวลาตอบสนองไม่เกิน 2 วินาที |

การทดสอบเพิ่มเติม:

- ตรวจว่ารหัสผ่านไม่ถูกจัดเก็บเป็น plain text
- ตรวจการรับส่งข้อมูลผ่าน HTTPS/TLS
- ตรวจว่าบัญชีที่ถูกระงับไม่สามารถสร้าง session
- ตรวจว่าผู้ใช้ที่ไม่มี session ไม่สามารถเข้าฟังก์ชันที่ต้อง Login
- ตรวจการแยกสิทธิ์ของแต่ละ role
- ตรวจ responsive layout ของหน้า Login
- ตรวจข้อความ error ไม่เปิดเผยข้อมูลบัญชีเกินความจำเป็น

## 7. ลำดับงาน

1. ตรวจสอบ `spec.md` และยืนยัน requirements กับทีม
2. กำหนดโครงสร้างข้อมูล `User` และ `Session`
3. สร้าง API สำหรับตรวจสอบข้อมูล Login
4. เพิ่มการตรวจสอบสถานะบัญชี
5. เพิ่มการตรวจสอบ password
6. เพิ่มระบบสร้าง session หลัง Login สำเร็จ
7. เพิ่มการตรวจสอบและส่งต่อ role
8. สร้างหน้า Login และแบบฟอร์ม username/email กับ password
9. เพิ่มข้อความแจ้งเตือนสำหรับข้อมูลไม่ถูกต้องและบัญชีถูกระงับ
10. เพิ่มการนำทางตาม role
11. เพิ่ม Session Guard สำหรับฟังก์ชันที่ต้อง Login
12. เชื่อมลิงก์สมัครสมาชิกและลืมรหัสผ่าน
13. เพิ่ม automated tests ตาม `AC-LOGIN-01` ถึง `AC-LOGIN-08`
14. ตรวจสอบ HTTPS ความปลอดภัย และ responsive layout
15. ตรวจสอบ traceability ระหว่าง `spec.md` และ implementation ก่อนส่งงาน

## 8. สิ่งที่ยังไม่ทำ

ฟังก์ชันต่อไปนี้จะไม่ถูกสร้างซ้ำภายใน UC-07:

- การสมัครสมาชิกโดยละเอียด
- การรีเซ็ตรหัสผ่านโดยละเอียด
- การจัดการข้อมูลบัญชีผู้ใช้
- การจัดการสิทธิ์เชิงลึกของแต่ละฟังก์ชัน

UC-07 มีหน้าที่หลักในการ:

1. ตรวจสอบตัวตนของผู้ใช้
2. ตรวจสอบสถานะบัญชี
3. สร้าง session เมื่อ authentication สำเร็จ
4. ระบุ role ของผู้ใช้
5. ป้องกันการเข้าถึงฟังก์ชันที่ต้อง Login หากไม่มี session
6. นำผู้ใช้ไปยังฟังก์ชันที่ตรงกับสิทธิ์
