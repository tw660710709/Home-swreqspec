# Feature: จองห้องพัก (Room Reservation)
Spec ID: SPEC-BKG-012 | Source: ข้อมูลการจองห้องพักจาก UC-12 | Use case: UC-12  
Owner: ทีมพัฒนาระบบหอพัก | Status: Draft v2 | Updated: 2569-09-20

## Goal
ผู้ใช้งานสามารถส่งคำขอจองห้องพักที่สถานะว่างได้ โดยระบบต้องตรวจสอบรายละเอียด ป้องกันการจองซ้ำซ้อนในเวลาเดียวกันอย่างเข้มงวด และแสดงผลการจองสำเร็จพร้อมเปลี่ยนสถานะห้องภายใน 2 วินาที 

## Scope

### In scope
- การแสดงรายละเอียดห้องพักและค่าใช้จ่ายก่อนยืนยันการจอง
- ฟอร์มสำหรับกรอกข้อมูลเพื่อขอจองห้องพัก (วันที่ย้ายเข้า, จำนวนคนพัก)
- การตรวจสอบสถานะความว่างของห้องแบบ Real-time ก่อนบันทึกการจอง
- การป้องกันการจองซ้ำซ้อน (Concurrency control / Race condition handling)
- การเปลี่ยนสถานะห้องพักหลังการจองสำเร็จเป็น "รอการยืนยัน"

### Out of scope
- การจ่ายเงินค่ามัดจำห้องผ่านระบบตัดบัตร/สแกนจ่าย
- การอนุมัติหรือปฏิเสธคำขอจองโดยเจ้าของหอพัก (ฟีเจอร์ฝั่ง Admin)
- การจัดทำสัญญาเช่าอิเล็กทรอนิกส์ (E-Contract)

## Constraints
- CON-SYS-01 ผู้ใช้ต้องผ่านการเข้าสู่ระบบ (Authenticated) เป็น Guest จึงจะสามารถเข้าหน้าฟอร์มจองได้ (Precondition)
- CON-BUS-01 ห้องพักที่จะจองต้องมีสถานะ "ว่างและสามารถจองได้" ก่อนโหลดหน้าจอ (Precondition)
- CON-UI-01 การแสดงผลฟอร์มต้องรองรับ Responsive ครบทุกอุปกรณ์

## Requirements
- FR-BKG-01 ระบบต้องแสดงรายละเอียดห้องและค่าใช้จ่ายให้ผู้ใช้ตรวจสอบก่อนจอง และมีตัวเลือกให้ดูรายละเอียดเพิ่มเติมได้ <- UC-12 main flow ขั้น 1-2, alternative 2a
- FR-BKG-02 ระบบต้องมีแบบฟอร์มให้กรอกข้อมูล (เช่น วันที่ย้ายเข้า) และแจ้งเตือนหากข้อมูลไม่ครบถ้วน <- UC-12 main flow ขั้น 3, exception 5b
- FR-BKG-03 ระบบต้องรองรับการกดยกเลิกการจอง โดยพากลับไปหน้ารายละเอียดห้องพักและไม่บันทึกข้อมูล <- UC-12 alternative 4a
- FR-BKG-04 เมื่อกดยืนยัน ระบบต้องตรวจสอบสถานะห้องล่าสุดอีกครั้ง หากห้องไม่ว่าง (ถูกจองไปแล้ว) ต้องแจ้งเตือนและให้เลือกใหม่ <- UC-12 main flow ขั้น 4-5, exception 5a
- FR-BKG-05 ถ้ายืนยันสำเร็จ ระบบต้องบันทึกข้อมูลจอง เปลี่ยนสถานะห้องเป็น "รอการยืนยัน" พร้อมแจ้งผลให้ทราบ <- UC-12 main flow ขั้น 6-7

## Quality Requirements
- NFR-PERF-01 วัดตั้งแต่ผู้ใช้กดยืนยันการจอง ระบบต้องบันทึกข้อมูลและตอบสนองเสร็จสิ้นด้วยค่า p95 <= 2 วินาทีในสภาวะเครือข่ายปกติ
- NFR-SEC-01 ระบบต้องมีกลไก Lock ในระดับ Database เพื่อป้องกันการจองห้องเดียวกันซ้ำในเวลาเดียวกัน (Race Condition Prevention)

## Acceptance Criteria
- [ ] AC-BKG-01 (FR-BKG-01, FR-BKG-02, FR-BKG-05, CON-SYS-01)
      Given ผู้ใช้เข้าสู่ระบบและอยู่ในหน้าห้องพักสถานะ "ว่าง"
      When  กรอกข้อมูลครบถ้วน และกดยืนยัน
      Then  ระบบบันทึกข้อมูลการจอง เปลี่ยนสถานะห้องเป็น "รอการยืนยัน" และแสดงหน้าผลสำเร็จ
- [ ] AC-BKG-02 (FR-BKG-04, NFR-SEC-01)
      Given ผู้ใช้ 2 คนพยายามกดยืนยันการจองห้องเดียวกันในเวลาเดียวกันพอดี (Race Condition)
      When  คำสั่งส่งถึงระบบ
      Then  ระบบประมวลผลสำเร็จเพียง 1 คน ส่วนอีกคนได้รับข้อความแจ้งเตือน "ห้องพักไม่ว่าง" 
- [ ] AC-BKG-03 (FR-BKG-02)
      Given ผู้ใช้กรอกฟอร์มไม่ครบ (เช่น ไม่ใส่วันที่ย้ายเข้า)
      When  กดยืนยันการจอง
      Then  ระบบแจ้งเตือนให้กรอกข้อมูลให้ครบ และไม่มีการบันทึกข้อมูล
- [ ] AC-BKG-04 (FR-BKG-03)
      Given ผู้ใช้อยู่ในหน้ากรอกข้อมูล
      When  กดปุ่ม "ยกเลิก"
      Then  ระบบพากลับหน้ารายละเอียดห้องพักและไม่บันทึกข้อมูลใดๆ
- [ ] AC-BKG-05 (CON-BUS-01, FR-BKG-04)
      Given ห้องพักถูกจองไปก่อนหน้าแล้ว (สถานะเป็นรอการยืนยัน หรือ ไม่ว่าง)
      When  ผู้ใช้พยายามเปิดหน้าจองห้องพักนั้นผ่าน URL
      Then  ระบบปฏิเสธการเข้าถึงและแจ้งว่าห้องไม่ว่าง
- [ ] AC-BKG-06 (NFR-PERF-01)
      Given ข้อมูลครบถ้วนและห้องว่าง
      When  ระบบดำเนินการตรวจสอบและบันทึก
      Then  เวลาตอบสนองจนแสดงผลสำเร็จต้องไม่เกิน 2 วินาที

## Assumptions & Open Questions
- ASM-01 สถานะห้องพักหลังถูกจองสำเร็จจะถูกล็อกที่ "รอการยืนยัน" (Pending Approval) อัตโนมัติ เพื่อกันคนอื่นเข้ามาจองซ้ำ
- ASM-02 ข้อมูลบังคับกรอกในฟอร์มจอง คือ วันที่คาดว่าจะย้ายเข้า และเบอร์โทรศัพท์ติดต่อ (หากยังไม่มีในโปรไฟล์)
- ASM-03 กลไก Locking (NFR-SEC-01) ใช้วิธี Database Row-level lock หรือ Transaction lock ฝั่ง Backend
